# SNN を p150a で速くする進め方

SEW-ResNet18 の推論を p150a で速くした記録（S1〜S34、`discrepancies.md` の D1〜D32）から、ほかの SNN でも使い回せる進め方、確かめ方、効いた手、落とし穴を抜き出した。新しいモデル（VGG、Spikformer、学習、再帰型など）の高速化を始めるときに、まずこれを読む。数値の出どころと細部は S 番号と D 番号から引く。環境、スクリプトの引数、確定した制約は `setup.md` にある。

各項目の末尾に、確かめた範囲を書く。

- 実測: SEW-ResNet18（T=4、224×224、fp32、batch 8、推論）で確かめた
- バージョン: tt-xla 1.4.0（pjrt-plugin-tt 1.4.0、同梱の tt-lang 1.1.5）での振る舞い。新しいバージョンでは変わりうる
- 推測: ほかのモデルでも同じになると見ているだけで、確かめていない

## 用語

| 用語 | 意味 |
| --- | --- |
| 1 ステップ | T 時刻ぶんの推論 1 回（`reset_net` から logits まで） |
| 1 ステップごとに同期 | 毎ステップ logits をホストに読み戻して待つ。結果を毎回使うときの時間 |
| まとめて同期 | k ステップを続けて送り、最後に 1 回だけ待つ。1 ステップあたりに直した値 |
| 送り出し | ホストが演算（プログラム）をデバイスに 1 つずつ送る仕事。演算の数に比例する |
| 稼働 | デバイスのプロファイラで測ったカーネルの区間の和 |
| 流し直し | tt-xla が書き出した TTNN の IR を、コンテナの ttnn で演算ごとに流し、演算ごとの稼働を測ること（`tools/ttnn-replay-ir.py`） |

## 1. 記録の要約

SEW-ResNet18 の 1 ステップ（まとめて同期）は 222.8 ms から 9.44 ms になった。TF32 の A30 は 7.52 ms。どの段も推論モードの BN、32 チャネルに埋めた stem、level 1、`WAIT=cpu` で測った値である。

| 段 | まとめて同期 | 1 ステップごとに同期 | 経緯 |
| --- | --- | --- | --- |
| 元の `SimpleLIFNode`（LIF を ttnn の小さな演算で流す） | 222.8 ms | 255.8 ms | S18 |
| LIF を tt-lang の 1 カーネルに（BN の出力の並び NCHW で呼ぶ） | 70.1 ms | 85.7 ms | S18 |
| LIF のカーネルを conv の出力の並びで呼ぶ（`nhwc4`） | 31.5 ms | 43.0 ms | S18、S19 |
| LIF の前後の `reshape` を消し、layer4 を `[1, T, R, C]` で渡す | 28.3 ms | 34.6 ms | S21、S23 |
| trace（`[T, N, C, H, W]` の入力のまま） | 21.1 ms | 27.2 ms | S23 |
| 入力をホストで conv の並びにして渡す（trace の下） | 17.1 ms | 22.7 ms | S23 |
| stem の conv を 2×2 で折りたたむ | 14.5 ms | 19.6 ms | S23 |
| stem の conv を時刻ごとに分け、LIF が分けた出力を直接読む | 11.9 ms | 17.3 ms | S24 |
| LIF のカーネルの計算を減らし、110 コアで動かす | 10.1 ms | 15.5 ms | S25〜S27 |
| 残差の足し算を LIF に取り込む | 9.59 ms | 14.2 ms | S30 |
| stem の conv を 16 枚 × 2 に、平均プーリングを行列積に | 9.44 ms | 15.0 ms | S32、S34 |
| （参考）A30、TF32 と `cudnn.benchmark` | 7.52 ms | 7.63 ms | S20 |
| （参考）A30、ベンチマークのまま（厳密な fp32） | 14.75 ms | — | S20 |

1 ステップごとに同期の値はホストの CPU の省電力のため回ごとに 1〜2 ms ぶれる（S31。CPU を起こしておくと S30 のバージョンで 11.0 ms）。S4〜S17 の値は、学習モードの BN、誤った stem の conv、デバイスの完了を待たない計時が混ざっていて、上の表とは比べられない（D21、D23、D24）。

## 2. 時間の出どころ

SEW-ResNet18 で分かった構造。ほかのモデルでも、ニューロンの層が多く、活性化が大きい間は同じ形になると見ている（推測）。

1. 1 ステップの時間はホストの送り出しとデバイスの稼働の遅い方で決まる。trace の前は送り出しが律速だった（1 ステップ 21.7 ms。trace で 1.5 ms。S23）。送り出しは演算 1 個あたり約 70〜360 µs で（測り方で違う。S11、S21、S23）、A30 の 12〜72 倍（S12）。（実測）
2. SNN ではニューロンを要素ごとの演算で書くと、層の数 × T × 約 7 個の演算になる。SEW-ResNet18 の LIF は約 1,900 演算で、送り出しの最大の出どころだった（S11、S14）。だから最初の仕事はニューロンを 1 層 1 カーネルにすることである（D16）。A30 でも、LIF を Triton の 1 カーネルにした `LIFNode` は `SimpleLIFNode` より約 7 ms 速い（S12）。（実測）
3. trace を入れた後は、流し直しの稼働がまとめて同期の時間をよく予測する（稼働 16.30 ms に対して実測 17.1 ms、9.19 ms に対して 9.44 ms。S23、S34）。trace の後は流し直しの内訳で次の手を選べる。（実測）
4. デバイスの稼働で最初に大きかったのは、conv よりも並べ替え（`reshape`、`permute`、`to_layout`）だった。タイル（32×32）の倍数でない形の並べ替えはデータの移動になり、1 回で約 1 ms かかる（layer4 の LIF の前後だけで 8.44 ms。S22）。ニューロンのカーネルを前後の演算と同じ並びで呼べば消える（S21、S23）。（実測）
5. 並べ替えを消すと、conv とニューロンが残る。stem を除く conv の稼働は A30（TF32）とほぼ同じで（S22）、LIF は DRAM の帯域でほぼ頭打ちになった（S27）。その先は活性化を L1 に置く（tt-xla からはできない。D30）、低い精度で持つ、など経路の外の手になる（S28、S29）。（実測）
6. スパイクは 0 と 1 で、SEW の ADD の和も小さな整数なので、どの精度でも正確に表せ、足しても丸めが入らない。このおかげで、残差の足し算をニューロンのカーネルに取り込み（S30）、平均プーリングを 0/1 の行列との積にしても（S34）、logits はビット単位で変わらなかった。スパイクを bf16 や bfp8 で持つ案は未着手（S29）。（実測）

## 3. 新しいモデルを始めるとき

1. 記録を読む: この文書、`discrepancies.md` の一覧と「判断の教訓」。p150a を使う前に、カードを使うほかのプロセスがないことを確かめる
2. 比べる相手を決める: A30 で SpikingJelly のベンチマークを流し、ベンチマークのコードで条件を確かめる。同じ組み方の自前のスクリプトでも測る（`tools/a30-sew18.py` が手本）。基準にする条件はユーザーに決めてもらう（4 節）
3. p150a で正しく動かす: ニューロンを純粋な PyTorch のもの（`SimpleLIFNode` など）に差し替え、BN は推論モード、`torch.compile(backend="tt")`、`venv-xla140` の level 1 で流す。段ごとに CPU と比べる（5 節）
4. 測り方をそろえる: `WAIT=cpu`、NUMA の固定、3 回の中央値、1 ステップごとに同期とまとめて同期の両方を出す（6 節）
5. 演算を数える: IR を書き出し（`xla-sew18.py` の `EXPORT=`）、TTNN の演算の数と種類を見る。ニューロンが何個の演算になっているかを数える
6. ニューロンを tt-lang のカーネルにする。前後の演算と同じ並びで呼ぶ（8 節）
7. trace を入れる
8. 内訳を出す: 流し直しで演算ごとの稼働を、A30 で層ごとの時間を測り、下限を見積もる。高速化の案の一覧を作る（7 節）
9. 案を 1 つずつ試す: 1 つ変えたら、logits がビット単位で同じか（数学を変えない変更なら）、3 回の時間、流し直しの差を見る。結果は作業記録に S 番号で、前提との食い違いは `discrepancies.md` に D 番号で書く
10. tt-xla の経路で取れない分は、流し直しで見込みを出し（`tools/ttnn-replay-chain.py`）、ttnn で直接書くかをユーザーに諮る

## 4. 比べる条件

- ベンチマークの条件はコードの該当行で確かめる。SEW-ResNet18 では推論の段の BN を学習モードと読み違えて p150a だけ学習モードで測り（D23。p150a に約 94 ms 不利）、A30 だけ TF32 を切った厳密な fp32 で比べていた（D26。A30 は TF32 を許すと 14.75 → 7.5 ms）。見る行は `model.train(...)`、`allow_tf32`、`cudnn.benchmark`、勾配の記録（`inference_mode` か `no_grad` か）、ウォームアップと計測の回数（S20）
- 精度: p150a の conv の出力は仮数 10 ビット相当（S19）。この記録の基準は TF32 の A30 とし、厳密な fp32 の値も併記した（ユーザーの決定、2026-10-28。D26）
- batch: SEW-ResNet18 は batch 12 以上で実行時に止まる（D12。バージョン）。A30 も同じ batch で測る
- ホストで済ませた前処理（入力の並べ替え、チャネル埋め、折りたたみ、時刻ごとの分割）は、p150a の時間に入らない。SEW-ResNet18 では trace の下で約 6.6 ms ぶん。比べるときに明記する（作業記録の「次にやること」）
- A30 でも 3 つの計時（CUDA event、1 ステップごとに同期、まとめて同期）を出す。A30 では 3 つがほぼ同じだが、p150a では違う（S20）
- ウォームアップ: A30 は TF32 を許すと最初の 12〜20 ステップが約 10 ms と遅い（S20）。p150a は最初の 9 ステップほどが遅い（S21）。どちらも長めに回してから測る

## 5. 正しさの確かめ方

- CPU の基準は同じプロセスで流し、同じ重みと入力を使う。推論モードの BN は、初期値の running stats のままだと活性が不自然になるので、CPU で一度 batch の統計を running stats に写してから両方に使う（S18）
- logits の相関だけで判断しない。出力の大半がバイアスだと、途中がおかしくなっていても相関は高く出る（D24）。段ごとに要素ごとに比べる（`xla-sew18.py` の `PREFIX=`）
- 相関が下げ止まる水準を、モデルごとに先に測る。CPU だけで、ある層の出力に相対 eps の乱れを入れ、種を変えて logits の相関を見る。SEW-ResNet18（初期値の重み、乱数の入力）では 1e-5 を超えると 0.92 前後で下げ止まった（S19）。デバイスの値がこの水準なら丸めの範囲で、大きく下がれば系統的な誤りがある
- 相関が下がったら、層ごとの出力の値の分布（スパイクの率、0〜3 の値の割合）を CPU と比べる。丸めはしきい値の近くの反転を散らすだけで、分布はほとんど変えない。分布がずれたら別の誤りがある（D25 では値 2 の割合が CPU の 0.44% に対して 2.74%）
- デバイスの丸めを CPU でまね、差を説明できるかを見る（`tools/lif-d22-emul.py`。D22 の切り捨てはデバイスとビット単位で一致。S19）
- スパイクの不一致は層を経るごとに増える（SEW-ResNet18 の layer4 で約 14%）。conv の丸めがしきい値の近くを反転させ、それが次の層の入力を動かすためで、網の性質である（S19。学習済みの重みと実際の画像では未確認）
- 数学を変えないはずの変更（並べ替えの削除、分割、融合）では、logits がビット単位で同じであることを求める。S24〜S34 はこれで確かめた。logits は `SAVE_LOGITS=` で保存しておく
- カーネルの単体試験には閾値ちょうど（h = 1、1 の 1 つ下と 1 つ上）と負の入力を入れる（S25、S27）
- チャネルの少ない conv を疑う。tt-xla 1.4.0 の level 1 は、入力が 3〜16 チャネルの stem の conv を誤って計算する（CPU との相関 0.21〜0.39）。32 チャネルにゼロで埋めると正しい（D24。バージョン）

## 6. 測り方

- デバイスの完了まで待つ。`torch_xla.sync(wait=True)` は待たない（D21。バージョン）。出力を `.cpu()` で読み戻すまでを測る（`WAIT=cpu`）。待たないと、休んだ直後と続けて回したときで値が最大 2 倍違う（D20）
- まとめて同期は送り出し（呼び出しが返るまで）と追いつき待ち（その後の完了待ち）に分ける（`xla-sew18.py` の `pipelined_split`）。送り出しが 1 ステップの時間とほぼ同じなら、ホストが律速である（S23）
- ホストの CPU を固定する。p150a は NUMA 5（`taskset -c 60-71,156-167`）、A30 は NUMA 6（`taskset -c 72-83,168-179`）
- 1 ステップごとに同期の時間は、待つたびにスレッドが眠り、CPU が 800 MHz のまま動くので、3〜5 ms 延びて回ごとにぶれる（D31）。プロセスごとに二峰に分かれたら、デバイスを疑う前に `tools/thread-sampler.py` で実際の周波数を見る。SMT の兄弟に SCHED_IDLE の空回りを置くと消えるが、計測の条件の変更なので、使ったかを書く
- 3 回の中央値を使う。まとめて同期はほとんどぶれず、1 ステップごとに同期は 1〜2 ms ぶれる（S24、S31）
- カーネルの時間はデバイスのプロファイラで測ったカーネルの区間から出す（コンテナで `tools/ttl-lif-bench.py`）。呼び出しの壁時計から帯域を出さない（D21）。プロファイラは CB の操作ごとに計測を足すので、小さなブロックを多く回すカーネルでは長めに出る（S16）
- tt-xla 1.4.0 の tt-metal は Tracy なしでビルドされていて、デバイスのプロファイラを使えない（S18。バージョン）。モデルの中の演算ごとの時間は流し直しで測る。コンテナの tt-metal はバージョンが違うので目安だが、trace の下の実測と 0.3〜0.8 ms 以内で合った（S23、S24、S34）
- 壁時計の 2 点から内訳を推測しない。batch を変えても変わらない部分は、演算の数に比例する送り出しかもしれない。本質的に削れないものでなければ「固定費」と呼ばない（D14、D16）

## 7. 時間を分ける

| 知りたいこと | 道具 | 経緯 |
| --- | --- | --- |
| 演算の数と種類 | `xla-sew18.py` の `EXPORT=<dir>`（IR）、`perf_metrics_file` | S6、S15 |
| 演算 1 個あたりの送り出しの費用 | `tools/xla-op-hostcost.py`（同じ演算を K 個つなぎ、K の差から出す） | S11、S23 |
| ホストとデバイスのどちらが律速か | `pipelined_split`。デバイスの仕事だけを減らす（画像を小さくする）比較 | S11、S23 |
| 部品ごとの費用 | 部品を外す比較（`NEURON=none`、`BN=none`） | S16、S18 |
| 演算ごとのデバイスの稼働 | `tools/ttnn-replay-ir.py`（流し直し） | S22 |
| A30 の層ごとの GPU の時間 | `tools/a30-sew18-profile.py`（層ごとに `record_function`） | S22 |
| 活性化を L1 に置いたらどうなるか | `tools/ttnn-replay-chain.py`（演算の出力をつないで流し直す） | S29 |
| 種類ごと、層ごとの内訳と下限 | `tools/breakdown-sew18.py` | S22、S28 |

- 下限の見積もり（S28）: 演算は 1 つずつ順に動き、各演算は max(読み書きの量 ÷ DRAM の帯域, 演算量 ÷ 演算性能) かかるとして足す。帯域は仕様の 512 GB/s と、読み書き半々の実測の約 390 GB/s（S25、S27）。演算性能は HiFi4、110 コアで 152 TFLOPS。fp32 で読み書きする限り、conv も演算より読み書きのほうが重い。SEW-ResNet18 では今の演算の並びの下限 4.08 ms（仕様の帯域）に対し、実測は 10.10 ms だった。種類ごとに下限との差を見ると、詰める先が分かる（S28 の時点では、LIF より conv のほうが差が大きかった）
- 案の一覧は、作業記録にある案の表（このリポジトリには含めていない）と同じ列で作る。列は、道、縮む分の上限、根拠の種類（実測、見積もり、推測）、状態、次の一歩、経緯。道は「tt-xla の範囲」と「ttnn で直接」に分け、ユーザーの判断が要る案は別にしておく
- 内訳と案の一覧はダッシュボードにまとめた（このリポジトリには含めていない。S22）

## 8. ニューロンのカーネル（tt-lang）

`tools/ttl_lif.py` が手本。式と制約は `setup.md` の「LIF の融合カーネル」にある。

構造:

- T のループをカーネルの中に持ち、膜電位を L1（DFB）に置いたまま T 時刻回す。1 時刻ぶんのブロックを全コアに分け、各コアが自分のブロックの T 時刻を順に処理する（S14、S25。実測）
- 今のカーネルは推論だけ、fp32、`SimpleLIFNode` のパラメータ（tau=2、hard reset など）に固定で、毎回膜電位 0 から始まる。SpikingJelly の multi-step を毎回 `reset_net` してから呼ぶのと同じ振る舞いで、single-step には未対応（`setup.md` の表）

tt-xla から呼ぶとき:

- `@tt_torch.tt_lang_operation(..., arg_roles=("in", "out"))` の中で、呼ぶたびにカーネルを作り直す。同じカーネルのオブジェクトを 2 回使うと、2 回目の resolve が失敗する（D18。バージョン）
- 出力先は呼び出しごとに別の値で埋めて渡す（`torch.full_like(x, -1.0 - k)`）。`torch.zeros_like` で作ると、tt-mlir が同じ形の定数を 1 つにまとめ、同じ形の層がすべて 1 つのバッファに書く。1 回しか呼ばない試験では表に出ない（D25。バージョン）
- grid を明示する（p150a は `11,10`）。`grid="auto"` は、tt-xla の経路では仮の 8×8 の Wormhole の device で決まり、64 コアで動く（D28。バージョン）
- 前後の演算と同じ並びで呼ぶ。tt-mlir は conv の出力を `[1, 1, N·H·W, C]` に置くので、カーネルはその形を受ける。torch の上では `[T, N, C, H, W]` を `[T·N, C, H, W]` に戻してから `permute(0, 2, 3, 1)` して渡す。すると tt-mlir が、conv を下ろすときに入る `permute` とこの並べ替えを組にして畳む。5 次元のまま `permute` すると畳まれない。この組になる場合のほかは、torch の上で足した `reshape` と `permute` を、tt-xla は畳まない（S16、S18、S21。バージョン）
- 時刻の境目をタイルの境目にそろえる。1 時刻の行数 R が 32 の倍数でないときは `[1, T, R, C]` で渡す。タイルは最後の 2 次元で切られるので、時刻ごとの行がタイルまで埋まる（S23）
- tt-lang のバージョンが 2 つある。コンテナは 1.1.10、tt-xla の wheel は 1.1.5 で、使える演算が違う（`>=`、`where` がない、`fill` の場所が違う、など。D19）。書いたら両方で通るかを毎回確かめる。コンテナで正しく動いても、tt-xla の経路のモデルの中でデバイスが止まったことがある（bf16 の出力のバージョン。`tt-smi -r` が要った。D29）

速さ:

- tt-lang は `store` ごとに DEST の区間を分けて初期化し直し、2 つの `store` に共通の部分式も別々に計算する。そのため計算が律速になりやすい（SEW-ResNet18 の LIF は約 7 割が計算だった。D27）
- 演算を減らす。h を運び、スパイクは `lt(0.99999994, h)`（fp32 で 1 の 1 つ下と比べれば h ≥ 1 と同じ）、リセットは `h · lt(h, 1)`、定数は `fill` で式の中に作る（CB に作ると、各コアの最初に重い区間が入る。S25、S27）
- ブロックは幅を広くする。同じタイル数なら、幅 1 の縦長は遅い。上限は 32 タイルで、入力の DFB が多いカーネルは小さくする（4 つなら 8 タイル。S25、S32）
- 律速は、計算だけのバージョン（DRAM を読み書きしない）と転送だけのバージョン（写すだけ）を作り、比べて切り分ける。生成された C++（`run-test.sh --emit-runner`）と `--auto-profile` で区間ごとの費用を見る（D27、S25）
- 到達点の目安: SEW-ResNet18 の LIF 20 層で 1.83 ms。読み書き半々の帯域での下限は約 1.63 ms、A30 は 1.54 ms（S27）。fp32 で読み書きする限り、A30 には届かない見込み（推測）

精度:

- 2 つの CB を直接足すと FPU で計算され、fp32 が仮数約 10 ビットに丸まる。SFPU を通る書き方（`v + (x − v)·0.5` など）なら、ttnn で直接動かすと CPU とビット単位で一致する（D22、S17）
- ただし tt-xla 1.4.0 の経路は、CB を読むたびに仮数 10 ビットへ切り捨てる（`UnpackToDestFp32` を運ばない）。SEW-ResNet18 では、ニューロンの入力（conv の出力）がすでに同じ精度なので、影響は conv の丸めより 2 桁小さかった（D22、S19。バージョン）

## 9. ニューロンの外で効いた手

| 手 | 効いた理由 | 効果（まとめて同期） | 経緯 |
| --- | --- | --- | --- |
| trace | 送り出しが 1 ステップ 21.7 → 1.5 ms | 28.3 → 21.1 ms | S23 |
| 入力をホストで conv の並び（`[1, 1, T·N·H·W, C]`）にして渡す | デバイスの `permute`（6.38 ms）が消える。trace の下でだけ効いた | 21.1 → 17.1 ms | S23 |
| チャネルの少ない stem の conv を 2×2 で折りたたむ（stride folding。tt-metal の ResNet-50 と同じ） | 入力の行が 1/4 になり、タイル化が 3.33 → 0.86 ms | 17.1 → 14.5 ms | S23 |
| 最も大きい活性化の conv を時刻ごとに分け、L1 に収める | DRAM を通る分割（22 プログラム）をやめる。stem の conv が 3.78 → 1.07 ms | 14.5 → 11.9 ms（下の行と合わせて） | S24 |
| 分けた conv の出力を、ニューロンのカーネルが直接読む | 結合（`concat`、0.5 ms）が消える | 上の行に含む | S24、S32 |
| 隣の要素ごとの演算をニューロンのカーネルに取り込む（SEW の残差の足し算） | 演算が 1 つ減り、読み書きも減る。スパイクの和は整数なので正確 | 10.10 → 9.59 ms | S30 |
| 並べ替えが要るプーリングを、0/1 の行列との積にする | タイルを埋めない形への並べ替えと `mean` が、`matmul` と掛け算になる（110 → 65 µs） | 9.48 → 9.44 ms | S34 |

- 時刻ごとに分けるのは、最も大きい活性化だけにする。小さい層の conv は分けると遅くなる（layer1 で 129 → 160 µs、layer4 で 175 → 338 µs。S29、S33）
- 推論モードの BN は、tt-mlir が conv に畳む。手で畳まない（D3）。例外は conv を分けて結合するときで、tt-mlir は結合をまたいで畳まないので、ホストで畳んだ（S24）

## 11. 進め方の教訓

細部は `discrepancies.md` の「判断の教訓」。以下は新しいモデルで特に効くもの。

- 移植ではライブラリの中心の部品（SNN ならニューロン）を先にターゲットのカーネルにする。最適化レベルや trace など周辺の設定の調査から入らない（D16）
- 回避策を勧める前、「動かない」と結論する前に、TT 側の実装（tt-xla のテスト、公式のベンチマーク）と、失敗したテストが何を流していたか（forward だけか backward もか）を読む（D3、D4）。公式の実行経路（`torch.compile(backend="tt")`）を先に試す（D5）
- ライブラリの使い方は手元のバージョンの文書とコードで確かめる。記憶にある古いバージョンの API で考えない（D1、D2、D11）
- ローカルの clone にある skill や文書は、upstream に同じ場所で残っているかを確かめてから「今の公式のもの」として扱う（D17）

## 12. ほかの SNN に広げるとき（未確認）

どれも SEW-ResNet18 では確かめていない。始めるときに先に確かめる。

| 変わる点 | 予想される影響 | 先に確かめること |
| --- | --- | --- |
| ニューロンの種類とパラメータ（IF、学習する tau の PLIF、soft reset、`decay_input=False` など） | カーネルの式と定数を変える。学習する tau は入力にする | 式ごとの CPU とのビット単位の一致、閾値ちょうどの例 |
| T が 4 でない | `make_lif` は任意の T を受ける。`make_lif4` と `make_lif2` は T = 4 専用 | 1 時刻の行数がタイルにそろうか |
| 残差がない（VGG）、ADD 以外の接続 | 残差の取り込みが使えないか、別の式になる。和が整数でなければ精度の扱いが変わる | 接続の式と値の範囲 |
| 注意を持つモデル（Spikformer） | matmul とニューロンが多い。カーネルを matmul の出力の並びに合わせる必要がある | 手元の SpikingJelly のコードで注意の計算の中身、正規化の層とそのモード |
| batch を上げる | SEW-ResNet18 は batch 12 以上で止まる（D12） | 新しいバージョンで直っているか |
| 学習 | ニューロンの backward（surrogate gradient）を別に書く。全時刻の膜電位を残す必要がある。conv の直後の学習モードの BN の backward が壊れる（D7） | D7 が 1.4.0 と公式の経路で起きるか |
| 再帰型、single-step | ある時刻の入力が前の時刻のスパイクに依存するので、時刻をまとめる multi-step の組み方が使えない。重みと膜電位を L1 に置いたまま時刻を回す 1 つのカーネルにできれば、GPU より向くというのがユーザーの見方（作業記録の「次にやること」） | 1 時刻ごとの呼び出しの送り出しの費用 |

## 13. ユーザーに判断を残すもの

この記録でユーザーに決めてもらったこと、または決めてもらうよう保留したもの。新しいモデルでも同じ扱いにする。

- 比べる基準（A30 の精度、batch、ホストで済ませる前処理を時間に入れるか）
- 精度を下げること（`math_fidelity`、bf16、bfp8）
- ホストの CPU の周波数の設定（sudo が要り、マシン全体と電力に影響する）
- デバイスが止まるおそれのある試し（止まると SIGTERM と `tt-smi -r` が要る）
- tt-xla の経路を出ること（ttnn で直接書く、`codegen_py`）
- GitHub への報告などの外部への投稿
