# SNN を p150a で高速化する手順

SEW-ResNet18 の推論を p150a で高速化した記録（S1〜S34、`discrepancies.md` の D1〜D32）から、他の SNN にも再利用できる手順、確認方法、効果のあった施策、落とし穴を抽出した。新しいモデル（VGG、Spikformer、学習、再帰型など）の高速化に着手する際は、まずこの文書を読む。数値の出典と詳細は S 番号と D 番号から参照する。環境、スクリプトの引数、確定した制約は `setup.md` に記載した。

各項目の末尾に、確認した範囲を記載する。

- 実測: SEW-ResNet18（T=4、224×224、fp32、batch 8、推論）で確認した。
- バージョン: tt-xla 1.4.0（pjrt-plugin-tt 1.4.0、同梱の tt-lang 1.1.5）での振る舞い。新しいバージョンでは変わりうる。
- 推測: 他のモデルでも同じになると予想しているだけで、確認していない。

## 用語

| 用語 | 意味 |
| --- | --- |
| 1 ステップ | T 時刻ぶんの推論 1 回（`reset_net` から logits まで） |
| 1 ステップごとに同期 | 毎ステップ、logits をホストへ転送して待機する。結果を毎回使用する場合の時間 |
| まとめて同期 | k ステップを続けて送信し、最後に 1 回だけ待機する。1 ステップあたりに換算した値 |
| ディスパッチ | ホストが演算（プログラム）をデバイスへ 1 つずつ送信する処理。演算の数に比例する |
| 稼働 | デバイスのプロファイラで測定したカーネルの区間の和 |
| 再実行（リプレイ） | tt-xla が出力した TTNN の IR を、コンテナの ttnn で演算ごとに実行し、演算ごとの稼働を測定すること（`tools/ttnn-replay-ir.py`） |

## 1. 記録の要約

SEW-ResNet18 の 1 ステップ（まとめて同期）は 222.8 ms から 9.44 ms に短縮した。TF32 の A30 は 7.52 ms。どの段階も、推論モードの BN、32 チャネルにゼロパディングした stem、level 1、`WAIT=cpu` で測定した値である。

| 段階 | まとめて同期 | 1 ステップごとに同期 | 経緯 |
| --- | --- | --- | --- |
| 元の `SimpleLIFNode`（LIF を ttnn の小さな演算で実装していた） | 222.8 ms | 255.8 ms | S18 |
| LIF を tt-lang の 1 カーネルに置換する（BN の出力の順序 NCHW で呼び出す） | 70.1 ms | 85.7 ms | S18 |
| LIF のカーネルを conv の出力の順序で呼び出す（`nhwc4`） | 31.5 ms | 43.0 ms | S18、S19 |
| LIF の前後の `reshape` を排除する。layer4 の LIF には `[1, T, R, C]` の形状で入力する | 28.3 ms | 34.6 ms | S21、S23 |
| trace を用いる（入力は `[T, N, C, H, W]` のまま） | 21.1 ms | 27.2 ms | S23 |
| 入力の順序をホストで conv と揃える（trace 使用時） | 17.1 ms | 22.7 ms | S23 |
| stem の conv を 2×2 の space-to-depth で変換する | 14.5 ms | 19.6 ms | S23 |
| stem の conv を時刻ごとに分割し、後段の LIF が分割した出力を直接ロードする | 11.9 ms | 17.3 ms | S24 |
| LIF のカーネルの計算を削減し、使用コアを 110 に増やす | 10.1 ms | 15.5 ms | S25〜S27 |
| 残差結合の加算を LIF と融合させる | 9.59 ms | 14.2 ms | S30 |
| stem の conv を 16 枚 × 2 に分割し、平均プーリングを行列積に置換する | 9.44 ms | 15.0 ms | S32、S34 |
| （参考）A30、TF32 と `cudnn.benchmark` | 7.52 ms | 7.63 ms | S20 |
| （参考）A30、ベンチマークの条件のまま（厳密な fp32） | 14.75 ms | — | S20 |

1 ステップごとに同期の値は、ホストの CPU の省電力機能のため、実行ごとに 1〜2 ms ばらつく（S31。CPU をアイドル状態にしないと、S30 のバージョンで 11.0 ms）。S4〜S17 の値には、学習モードの BN、誤った stem の conv、デバイスの完了を待機しない計時が混在しているため、上の表とは比較できない（D21、D23、D24）。

## 2. 時間の要因

SEW-ResNet18 で判明した構造。他のモデルでも、ニューロンの層が多く、活性化が大きい限りは同じ構造になると考えている（推測）。

1. 1 ステップの時間は、ホストのディスパッチとデバイスの稼働のうち遅い方で決まる。trace の導入前はディスパッチが律速だった（1 ステップ 21.7 ms。trace で 1.5 ms。S23）。ディスパッチのコストは演算 1 個あたり約 70〜360 µs で（測定方法で異なる。S11、S21、S23）、A30 の 12〜72 倍（S12）。（実測）
2. SNN でニューロンを要素ごとの演算で記述すると、層の数 × T × 約 7 個の演算になる。SEW-ResNet18 の LIF は約 1,900 演算で、ディスパッチの最大の要因だった（S11、S14）。そのため、最初に行うべきは、ニューロンを 1 層につき 1 カーネルに融合することである（D16）。A30 でも、LIF を Triton の 1 カーネルにした `LIFNode` は `SimpleLIFNode` より約 7 ms 速い（S12）。（実測）
3. trace の導入後は、再実行で得た稼働が、まとめて同期の時間をよく予測する（稼働 16.30 ms に対して実測 17.1 ms、9.19 ms に対して 9.44 ms。S23、S34）。そのため trace の導入後は、再実行の内訳から次の施策を選択できる。（実測）
4. デバイスの稼働のうち、当初大きかったのは conv よりも並べ替え（`reshape`、`permute`、`to_layout`）だった。タイル（32×32）の倍数でない形状の並べ替えはデータの移動を伴い、1 回あたり約 1 ms かかる（layer4 の LIF の前後だけで 8.44 ms。S22）。ニューロンのカーネルを前後の演算と同じ順序で呼び出せば、これらの並べ替えは不要になる（S21、S23）。（実測）
5. 並べ替えを排除すると、conv とニューロンが残る。stem を除く conv の稼働は A30（TF32）とほぼ同等で（S22）、LIF は DRAM 帯域の上限にほぼ達した（S27）。それ以上の短縮には、活性化を L1 に配置する（tt-xla からは指定できない。D30）、低い精度で保持する、など tt-xla の経路の外の施策が必要になる（S28、S29）。（実測）
6. スパイクは 0 か 1 で、SEW の ADD の和も小さな整数であるため、どの精度でも正確に表現でき、加算しても丸め誤差が生じない。そのため、残差結合の加算をニューロンのカーネルと融合しても（S30）、平均プーリングを 0/1 の行列との積に置換しても（S34）、logits はビット単位で一致した。スパイクを bf16 や bfp8 で保持する案は未着手（S29）。（実測）

## 3. 新しいモデルに着手するとき

1. 記録を読む: この文書と、`discrepancies.md` の一覧と「判断の教訓」。p150a を使用する前に、カードを使用している他のプロセスがないことを確認する。
2. 比較対象を決める: A30 で SpikingJelly のベンチマークを実行し、ベンチマークのコードで条件を確認する。同じ構成の自前のスクリプトでも測定する（`tools/a30-sew18.py` が手本）。基準にする条件はユーザーに決めてもらう（4 節）。
3. p150a で正しく実行する: ニューロンを純粋な PyTorch の実装（`SimpleLIFNode` など）に置換し、BN を推論モードにして、`torch.compile(backend="tt")` と `venv-xla140` の level 1 で実行する。モデルの段ごとに CPU と比較する（5 節）。
4. 測定方法を揃える: `WAIT=cpu`、NUMA ノードへの固定、3 回の中央値を用い、1 ステップごとに同期とまとめて同期の両方を算出する（6 節）。
5. 演算を数える: IR を出力し（`xla-sew18.py` の `EXPORT=`）、TTNN の演算の数と種類を確認する。ニューロンが何個の演算になっているかを数える。
6. ニューロンを tt-lang のカーネルに置換する。前後の演算と同じ順序で呼び出す（8 節）。
7. trace を導入する。
8. 内訳を算出する: 再実行で演算ごとの稼働を、A30 で層ごとの時間を測定し、下限を見積もる。高速化の案の一覧を作成する（7 節）。
9. 案を 1 つずつ試す: 1 つ変更するたびに、logits がビット単位で一致するか（数学的に等価な変更の場合）、3 回の時間、再実行の差を確認する。結果は作業記録に S 番号で、前提との相違は `discrepancies.md` に D 番号で記載する。
10. tt-xla の経路では得られない短縮は、再実行で見込みを算出し（`tools/ttnn-replay-chain.py`）、ttnn で直接記述するかをユーザーに諮る。

## 4. 比較の条件

- ベンチマークの条件はコードの該当行で確認する。SEW-ResNet18 では、ベンチマークの推論のフェーズの BN を学習モードと読み違えて p150a だけを学習モードで測定し（D23。p150a に約 94 ms 不利）、A30 だけを TF32 を無効にした厳密な fp32 で比較していた（D26。A30 は TF32 を有効にすると 14.75 → 7.5 ms）。確認する行は `model.train(...)`、`allow_tf32`、`cudnn.benchmark`、勾配の記録（`inference_mode` か `no_grad` か）、ウォームアップと計測の回数（S20）。
- 精度: p150a の conv の出力は仮数 10 ビット相当（S19）。この記録の基準は TF32 の A30 とし、厳密な fp32 の値も併記した（ユーザーの決定、2026-10-28。D26）。
- batch: SEW-ResNet18 は batch 12 以上で実行時にエラーになる（D12。バージョン）。A30 も同じ batch で測定する。
- ホスト側の前処理（入力の並べ替え、チャネルのゼロパディング、space-to-depth、時刻ごとの分割）は、p150a の時間に含まれない。SEW-ResNet18 では trace 使用時で約 6.6 ms。比較する際に明記する（作業記録の「次にやること」）。
- A30 でも 3 つの計時（CUDA event、1 ステップごとに同期、まとめて同期）を測定する。A30 では 3 つがほぼ同じだが、p150a では異なる（S20）。
- ウォームアップ: A30 は TF32 を有効にすると、最初の 12〜20 ステップが約 10 ms と遅い（S20）。p150a は最初の 9 ステップほどが遅い（S21）。どちらも長めにウォームアップしてから測定する。

## 5. 正確性の確認方法

- CPU の基準は同じプロセスで実行し、同じ重みと入力を用いる。推論モードの BN は、running stats が初期値のままだと活性化が不自然になるため、CPU で一度 batch の統計を running stats に複製してから両方で用いる（S18）。
- logits の相関だけで判断しない。出力の大半がバイアスの場合、途中の層が誤っていても相関は高くなる（D24）。モデルの段ごとに要素単位で比較する（`xla-sew18.py` の `PREFIX=`）。
- 相関が下げ止まる水準を、モデルごとに先に測定する。CPU のみで、ある層の出力に相対 eps の摂動を加え、乱数のシードを変えて logits の相関を確認する。SEW-ResNet18（初期値の重み、乱数の入力）では、eps が 1e-5 を超えると相関は 0.92 前後で下げ止まった（S19）。デバイスの値がこの水準なら丸め誤差の範囲内で、大きく下回れば系統的な誤りがある。
- 相関が低下したら、層ごとの出力の値の分布（発火率、0〜3 の値の割合）を CPU と比較する。丸めはしきい値近傍のスパイクを散発的に反転させるだけで、分布はほとんど変えない。分布がずれていれば、別の誤りがある（D25 では値 2 の割合が CPU の 0.44% に対して 2.74%）。
- デバイスの丸めを CPU で模倣し、差を説明できるかを確認する（`tools/lif-d22-emul.py`。D22 の切り捨てはデバイスとビット単位で一致。S19）。
- スパイクの不一致は層を経るごとに増加する（SEW-ResNet18 の layer4 で約 14%）。conv の丸めがしきい値近傍のスパイクを反転させ、それが次の層の入力を変えるためで、ネットワークの性質である（S19。学習済みの重みと実際の画像では未確認）。
- 数学的に等価なはずの変更（並べ替えの削除、分割、融合）では、logits がビット単位で一致することを要求する。S24〜S34 はこの方法で確認した。logits は `SAVE_LOGITS=` で保存しておく。
- カーネルの単体テストには、しきい値ちょうどの値（h = 1、1 の 1 つ下と 1 つ上）と負の入力を含める（S25、S27）。
- チャネル数の少ない conv を疑う。tt-xla 1.4.0 の level 1 は、入力が 3〜16 チャネルの stem の conv を誤って計算する（CPU との相関 0.21〜0.39）。32 チャネルにゼロパディングすると正しく計算される（D24。バージョン）。

## 6. 測定方法

- デバイスの完了まで待機する。`torch_xla.sync(wait=True)` は待機しない（D21。バージョン）。出力を `.cpu()` でホストへ転送するまでを測定する（`WAIT=cpu`）。待機しないと、デバイスのアイドル直後と連続実行時とで値が最大 2 倍異なる（D20）。
- まとめて同期の時間は、ディスパッチ（呼び出しが返るまで）と、その後の完了待ち（デバイスがホストに追いつくまで）に分割する（`xla-sew18.py` の `pipelined_split`）。ディスパッチの時間が 1 ステップの時間とほぼ同じなら、ホストが律速である（S23）。
- ホストのスレッドを CPU に固定する。p150a は NUMA 5（`taskset -c 60-71,156-167`）、A30 は NUMA 6（`taskset -c 72-83,168-179`）。
- 1 ステップごとに同期の時間は、待機のたびにスレッドがスリープし、CPU が 800 MHz のまま動作するため、3〜5 ms 延び、実行ごとにばらつく（D31）。プロセスごとに値が二峰に分かれたら、デバイスを疑う前に `tools/thread-sampler.py` で実際の周波数を確認する。SMT の兄弟スレッドに SCHED_IDLE のビジーループを置くと解消するが、計測の条件の変更であるため、用いたかどうかを記載する。
- 3 回の中央値を用いる。まとめて同期はほとんどばらつかず、1 ステップごとに同期は 1〜2 ms ばらつく（S24、S31）。
- カーネルの時間は、デバイスのプロファイラで測定したカーネルの区間から算出する（コンテナで `tools/ttl-lif-bench.py`）。呼び出しの壁時計時間から帯域を算出しない（D21）。プロファイラは CB の操作ごとに計測を追加するため、小さなブロックを多数処理するカーネルでは長めに測定される（S16）。
- tt-xla 1.4.0 の tt-metal は Tracy なしでビルドされており、デバイスのプロファイラを使用できない（S18。バージョン）。モデル内の演算ごとの時間は再実行で測定する。コンテナの tt-metal はバージョンが異なるため目安の値だが、trace 使用時の実測と 0.3〜0.8 ms 以内で一致した（S23、S24、S34）。
- 壁時計時間の 2 点から内訳を推測しない。batch を変えても変わらない部分は、演算の数に比例するディスパッチの時間かもしれない。本質的に削減できないものでなければ「固定費」と呼ばない（D14、D16）。

## 7. 時間の分解

| 知りたいこと | ツール | 経緯 |
| --- | --- | --- |
| 演算の数と種類 | `xla-sew18.py` の `EXPORT=<dir>`（IR）、`perf_metrics_file` | S6、S15 |
| 演算 1 個あたりのディスパッチのコスト | `tools/xla-op-hostcost.py`（同じ演算を K 個直列に適用し、K の差から算出する） | S11、S23 |
| ホストとデバイスのどちらが律速か | `pipelined_split`。デバイスの処理量だけを削減する（画像を小さくする）比較 | S11、S23 |
| 構成要素ごとのコスト | 構成要素を除いた比較（`NEURON=none`、`BN=none`） | S16、S18 |
| 演算ごとのデバイスの稼働 | `tools/ttnn-replay-ir.py`（再実行） | S22 |
| A30 の層ごとの GPU の時間 | `tools/a30-sew18-profile.py`（層ごとに `record_function`） | S22 |
| 活性化を L1 に配置した場合の効果 | `tools/ttnn-replay-chain.py`（前の演算の出力を入力にして再実行する） | S29 |
| 種類ごと、層ごとの内訳と下限 | `tools/breakdown-sew18.py` | S22、S28 |

- 下限の見積もり（S28）: 演算は 1 つずつ順に実行され、各演算に max(読み書きの量 ÷ DRAM の帯域, 演算量 ÷ 演算性能) の時間がかかるとして合計する。帯域は仕様の 512 GB/s と、読み書き半々での実測の約 390 GB/s（S25、S27）。演算性能は HiFi4、110 コアで 152 TFLOPS。fp32 で読み書きする限り、conv でも演算より読み書きのほうが時間を要する。SEW-ResNet18 では、現在の演算の構成での下限 4.08 ms（仕様の帯域）に対し、実測は 10.10 ms だった。種類ごとに下限との差を比較すると、短縮の余地が大きい箇所が分かる（S28 の時点では、LIF より conv のほうが差が大きかった）。
- 案の一覧は、作業記録にある案の表（このリポジトリには含めていない）と同じ列で作成する。列は、経路、短縮量の上限、根拠の種類（実測、見積もり、推測）、状態、次の作業、経緯。経路は「tt-xla の範囲」と「ttnn で直接」に分け、ユーザーの判断を要する案は別にしておく。
- 内訳と案の一覧はダッシュボードにまとめた（このリポジトリには含めていない。S22）。

## 8. ニューロンのカーネル（tt-lang）

`tools/ttl_lif.py` が手本。式と制約は `setup.md` の「LIF の融合カーネル」に記載した。

構造:

- T のループをカーネル内に持ち、膜電位を L1（DFB）に保持したまま T 時刻分を処理する。1 時刻分のブロックを全コアに分配し、各コアが担当するブロックの T 時刻を順に処理する（S14、S25。実測）。
- 現在のカーネルは推論のみ、fp32、`SimpleLIFNode` のパラメータ（tau=2、hard reset など）に固定で、毎回膜電位 0 から開始する。SpikingJelly の multi-step を毎回 `reset_net` してから呼び出すのと同じ振る舞いで、single-step には未対応（`setup.md` の表）。

tt-xla から呼び出すとき:

- `@tt_torch.tt_lang_operation(..., arg_roles=("in", "out"))` の中で、呼び出すたびにカーネルを生成し直す。同じカーネルのオブジェクトを 2 回使用すると、2 回目の resolve が失敗する（D18。バージョン）。
- 出力先のテンソルは、呼び出しごとに異なる値で初期化して渡す（`torch.full_like(x, -1.0 - k)`）。`torch.zeros_like` で作成すると、tt-mlir が同じ形状の定数を 1 つに統合し、同じ形状の層がすべて 1 つのバッファに書き込む。1 回しか呼び出さないテストでは顕在化しない（D25。バージョン）。
- grid を明示する（p150a は `11,10`）。`grid="auto"` は、tt-xla の経路では仮の 8×8 の Wormhole の device に基づいて決まり、64 コアで実行される（D28。バージョン）。
- 前後の演算と同じ順序で呼び出す。tt-mlir は conv の出力を `[1, 1, N·H·W, C]` の形状で配置するため、カーネルはその形状で受け取る。torch の上では `[T, N, C, H, W]` を `[T·N, C, H, W]` に戻してから `permute(0, 2, 3, 1)` して渡す。すると tt-mlir は、conv の lowering で挿入される `permute` とこの並べ替えを対にして相殺し、除去する。5 次元のまま `permute` すると相殺されない。この対になる場合を除き、torch の上で追加した `reshape` と `permute` を tt-xla は除去しない（S16、S18、S21。バージョン）。
- 時刻の境界をタイルの境界に揃える。1 時刻の行数 R が 32 の倍数でないときは `[1, T, R, C]` の形状で渡す。タイルは最後の 2 次元で分割されるため、時刻ごとの行がタイル単位までパディングされる（S23）。
- tt-lang のバージョンが 2 つある。コンテナは 1.1.10、tt-xla の wheel は 1.1.5 で、使用できる演算が異なる（`>=`、`where` がない、`fill` の所属するモジュールが異なる、など。D19）。カーネルを記述したら、両方で動作するかを毎回確認する。コンテナで正しく動作しても、tt-xla の経路のモデル内でデバイスがハングしたことがある（bf16 の出力のバージョン。`tt-smi -r` が必要だった。D29）。

速度:

- tt-lang は `store` ごとに DEST の区間を分割して初期化し直し、2 つの `store` に共通する部分式も別々に計算する。そのため計算が律速になりやすい（SEW-ResNet18 の LIF は約 7 割が計算だった。D27）。
- 演算を削減する。時刻をまたいで h を保持し、スパイクは `lt(0.99999994, h)`（fp32 で 1 の 1 つ下の値と比較すれば h ≥ 1 と等価）、リセットは `h · lt(h, 1)` で計算し、定数は `fill` で式の中に生成する（CB に生成すると、各コアの冒頭に重い区間が入る。S25、S27）。
- ブロックの幅を広くする。同じタイル数なら、幅 1 の縦長のブロックは遅い。上限は 32 タイルで、入力の DFB が多いカーネルではブロックを小さくする（4 つなら 8 タイル。S25、S32）。
- 律速要因は、計算のみのバージョン（DRAM を読み書きしない）と転送のみのバージョン（コピーのみ）を作成し、比較して切り分ける。生成された C++（`run-test.sh --emit-runner`）と `--auto-profile` で区間ごとのコストを確認する（D27、S25）。
- 到達点の目安: SEW-ResNet18 の LIF 20 層で 1.83 ms。読み書き半々の帯域での下限は約 1.63 ms、A30 は 1.54 ms（S27）。fp32 で読み書きする限り、A30 には及ばない見込み（推測）。

精度:

- 2 つの CB を直接加算すると FPU で計算され、fp32 が仮数約 10 ビットに丸められる。SFPU を経由する記述（`v + (x − v)·0.5` など）なら、ttnn で直接実行した場合に CPU とビット単位で一致する（D22、S17）。
- ただし tt-xla 1.4.0 の経路では、CB を読み出すたびに仮数 10 ビットへ切り捨てられる（`UnpackToDestFp32` が引き継がれない）。SEW-ResNet18 では、ニューロンの入力（conv の出力）がすでに同じ精度であるため、影響は conv の丸めより 2 桁小さかった（D22、S19。バージョン）。

## 9. ニューロン以外で効果のあった施策

| 施策 | 効果があった理由 | 効果（まとめて同期） | 経緯 |
| --- | --- | --- | --- |
| trace | ディスパッチが 1 ステップあたり 21.7 → 1.5 ms | 28.3 → 21.1 ms | S23 |
| 入力の順序をホストで conv と揃える（`[1, 1, T·N·H·W, C]`） | デバイスの `permute`（6.38 ms）が不要になる。trace 使用時にのみ効果があった | 21.1 → 17.1 ms | S23 |
| チャネル数の少ない stem の conv を 2×2 の space-to-depth で変換する（stride folding。tt-metal の ResNet-50 と同じ） | 入力の行数が 1/4 になり、タイル化が 3.33 → 0.86 ms | 17.1 → 14.5 ms | S23 |
| 活性化が最大の conv を時刻ごとに分割し、L1 に収める | DRAM を経由する分割（22 プログラム）を回避する。stem の conv が 3.78 → 1.07 ms | 14.5 → 11.9 ms（下の行との合計） | S24 |
| 分割した conv の出力を、ニューロンのカーネルが直接ロードする | 結合（`concat`、0.5 ms）が不要になる | 上の行に含む | S24、S32 |
| 隣接する要素ごとの演算をニューロンのカーネルと融合する（SEW の残差結合の加算） | 演算が 1 つ減り、読み書きも減る。スパイクの和は整数であるため正確 | 10.10 → 9.59 ms | S30 |
| 並べ替えを要するプーリングを、0/1 の行列との積に置換する | タイルを埋めない形状への並べ替えと `mean` が、`matmul` と乗算に置換される（110 → 65 µs） | 9.48 → 9.44 ms | S34 |

- 時刻ごとの分割は、最も大きい活性化に限る。小さい層の conv は分割すると遅くなる（layer1 で 129 → 160 µs、layer4 で 175 → 338 µs。S29、S33）。
- 推論モードの BN は、tt-mlir が conv に統合する（BN folding）。手動で統合しない（D3）。例外は conv を分割して結合するときで、tt-mlir は結合をまたいで統合しないため、ホストで統合した（S24）。

## 11. 進め方の教訓

詳細は `discrepancies.md` の「判断の教訓」に記載した。以下は新しいモデルで特に有用なもの。

- 移植では、ライブラリの中核となる構成要素（SNN ならニューロン）を先にターゲットのカーネルに置換する。最適化レベルや trace など周辺の設定の調査から始めない（D16）。
- 回避策を提案する前、「動かない」と結論する前に、TT 側の実装（tt-xla のテスト、公式のベンチマーク）と、失敗したテストが何を実行していたか（forward のみか backward もか）を読む（D3、D4）。公式の実行経路（`torch.compile(backend="tt")`）を先に試す（D5）。
- ライブラリの使用方法は、手元のバージョンの文書とコードで確認する。記憶にある古いバージョンの API を前提にしない（D1、D2、D11）。
- ローカルの clone にある skill や文書は、upstream の同じ場所に残っているかを確認してから「現在の公式のもの」として扱う（D17）。

## 12. 他の SNN に適用するとき（未確認）

いずれも SEW-ResNet18 では確認していない。着手する際に先に確認する。

| 変わる点 | 予想される影響 | 先に確認すること |
| --- | --- | --- |
| ニューロンの種類とパラメータ（IF、学習する tau の PLIF、soft reset、`decay_input=False` など） | カーネルの式と定数を変更する。学習する tau はカーネルの入力にする | 式ごとの CPU とのビット単位の一致、しきい値ちょうどの例 |
| T が 4 でない | `make_lif` は任意の T を受け付ける。`make_lif4` と `make_lif2` は T = 4 専用 | 1 時刻の行数がタイルの境界に揃うか |
| 残差結合がない（VGG）、ADD 以外の残差結合 | 残差結合の融合が使えないか、別の式になる。和が整数でなければ精度の扱いが変わる | 残差結合の式と値の範囲 |
| 注意機構を持つモデル（Spikformer） | matmul とニューロンが多い。カーネルを matmul の出力の順序に合わせる必要がある | 手元の SpikingJelly のコードでの注意機構の計算の内容、正規化層とそのモード |
| batch を増やす | SEW-ResNet18 は batch 12 以上でエラーになる（D12） | 新しいバージョンで修正されているか |
| 学習 | ニューロンの backward（surrogate gradient）を別に記述する。全時刻の膜電位を保持する必要がある。conv の直後の学習モードの BN の backward の勾配が誤る（D7） | D7 が 1.4.0 と公式の経路で発生するか |
| 再帰型、single-step | ある時刻の入力が前の時刻のスパイクに依存するため、時刻をまとめて処理する multi-step の構成が使えない。重みと膜電位を L1 に保持したまま時刻を進める 1 つのカーネルにできれば、GPU より適しているというのがユーザーの見方（作業記録の「次にやること」） | 1 時刻ごとの呼び出しのディスパッチのコスト |

## 13. ユーザーに判断を残すもの

この記録でユーザーに決めてもらったこと、または決めてもらうよう保留したもの。新しいモデルでも同じ扱いにする。

- 比較の基準（A30 の精度、batch、ホスト側の前処理を時間に含めるか）
- 精度を下げること（`math_fidelity`、bf16、bfp8）
- ホストの CPU の周波数の設定（sudo が必要で、マシン全体と電力に影響する）
- デバイスがハングするおそれのある試行（ハングすると SIGTERM と `tt-smi -r` が必要になる）
- tt-xla の経路から外れること（ttnn で直接記述する、`codegen_py`）
- GitHub への報告などの外部への投稿
